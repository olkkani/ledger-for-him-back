## Problem Statement

Building a personal 가계부 (household ledger) backend in Kotlin/Spring Boot. When the user logs a new transaction, they currently have to type/select a `category` by hand every time. The goal is to recommend the top candidate `category` values so entry needs as few taps as possible — ideally the correct category is already top-1 before the user even opens the picker.

## What Makes This Cool

"태그 0탭 입력" — zero-tap category entry. Not just "show a ranked list" but the aspiration that the top recommendation is right often enough that a future client could pre-select it and the user just confirms. The recommendation should visibly track two different signals depending on how far into entry the user is — before typing an amount, it should already feel like it "knows" what's coming next.

## Constraints

- Personal-scale data: same order of magnitude as the sibling `description`-recommendation design (hundreds to low-thousands of transactions/year). Real-time in-memory/single-query scoring is sufficient — no pre-aggregation table.
- Backend-only API — no client code exists in this repo (confirmed: scope stays backend, matching the sibling design).
- `transactions.category` already exists in the schema (`V1.1__create-tables.sql`) — no migration needed for this design.
- Stack: Kotlin, Spring Boot, jOOQ + Flyway, Postgres, Testcontainers — same as the rest of the repo.

## Premises

1. **Staged replacement model, not a combined weighted sum.** Before an amount is entered (Stage 1): time-of-day + day-of-week signal, plus a boost for the category of the user's immediately-preceding transaction. Once an amount is entered (Stage 2): time/dow signal + amount-similarity signal; the prior-category boost drops out entirely — it does not persist alongside amount similarity. — agreed
2. **Separate, independent endpoint** from the existing `GET /api/transactions/recommendations` (description recommendation). No shared scoring code is assumed; this design does not modify the sibling design. — agreed
3. **Backend-only design.** "0-tap" is the UX aspiration a future client would implement (auto-selecting top-1); this design's job stops at producing a candidate list good enough for that to make sense later. — agreed
4. **Weights determined by backtest, not intuition** — same strategy as the sibling `description`-recommendation design, using the same ~1 year of real transaction history. — agreed

## Approaches Considered

### Approach A: Staged independent queries (chosen)
One endpoint, two code paths selected by whether `amount` is present in the request. Stage 1 query: `GROUP BY category` scored by time/dow similarity + prior-category match (boolean boost). Stage 2 query: `GROUP BY category` scored by time/dow similarity + amount similarity. Each stage is its own simple SQL aggregation + score, no shared weighted-sum formula. Fastest to build; mirrors the sibling design's per-request aggregation pattern.

### Approach B: Unified weighted-sum scorer (rejected)
One formula `score = w1*timeSim + w2*amountSim + w3*priorCategorySim`, zeroing out whichever term doesn't apply per stage. Rejected — a single formula that silently zeroes terms doesn't match user intent ("완전 대체", not blend); it invites weight interactions the user explicitly said they don't want, and would need per-stage backtesting anyway, so the "one formula" simplicity is illusory.

### Approach C: Markov category-transition model (rejected for this pass)
Model category → category transition probability (e.g. 장보기 → 외식 pattern) instead of a static prior-category boost. Most true-to-"understand my life pattern," but highest implementation/validation complexity for personal-scale data. Deferred — Stage 1's simple prior-category boost is a degenerate case of this and can be upgraded later if backtest shows the boost underperforms.

## Recommended Approach

**Approach A: Staged independent queries.**

```
GET /api/transactions/recommendations/category?amount={BigDecimal, optional}&targetDateTime={ISO-8601, optional, default=now}

user_id from Spring Security principal (same rule as sibling design — never client-supplied)

Response: List<CategoryCandidate> (max 5)
  - category: String
  - score: Double
  - frequency: Int
```

**Stage selection:** presence of `amount` in the request selects the stage. No separate `stage` param — the client naturally calls this with amount omitted before the amount field is filled, and with amount included after.

**Stage 1 (no amount) scoring:**
```
score = w_time * timeSim(targetDateTime.hour, category.typicalHour)
      + w_dow  * dowSim(targetDateTime.dayOfWeek, category.typicalDow)
      + w_prior * (1 if category == mostRecentTransaction.category else 0)
```

**Stage 2 (amount present) scoring:**
```
score = w_time   * timeSim(targetDateTime.hour, category.typicalHour)
      + w_amount * amountSim(inputAmount, category.avgAmount)
```
`priorCategory` term is absent entirely in Stage 2 — not zero-weighted, structurally removed, per premise 1.

**Reused formulas** (identical to the sibling design, same repo, same conventions — do not reinvent):
```
hourDistance = min(|h1 - h2|, 24 - |h1 - h2|)
timeSim   = 1 - min(hourDistance / 12, 1)
dowSim    = 1 if same weekday/weekend bucket else 0.3
amountSim = 1 - min(|abs(input) - abs(avg)| / max(abs(avg), 1), 1)   // abs value, sign-independent
```

**"Most recent transaction"** for the Stage 1 prior-category boost = the user's single latest transaction with `occurred_at < targetDateTime` (same future-leak boundary as the sibling design's `history_strictly_before`).

**Candidate aggregation** — `GROUP BY TRIM(LOWER(category))`, same normalization as the sibling `description` design. `category` is **not** assumed enum-like: `excel-import-transaction-schema.md` (open question, line 105) explicitly leaves `category`(분류) as free text with no lookup table, so this design must not assume a controlled vocabulary. Without normalization, "식비" and "식비 " (or casing variants from manual entry) would silently split into separate candidates. The response returns the most-recently-used original spelling for the group, not the normalized key — same convention as `description`.

```sql
SELECT TRIM(LOWER(category)) AS normalized_category,
       (ARRAY_AGG(category ORDER BY occurred_at DESC))[1] AS category,  -- most recent original spelling
       AVG(ABS(amount)) AS avg_amount,
       ATAN2(AVG(SIN(2*PI()*EXTRACT(HOUR FROM occurred_at AT TIME ZONE 'Asia/Seoul')/24)),
             AVG(COS(2*PI()*EXTRACT(HOUR FROM occurred_at AT TIME ZONE 'Asia/Seoul')/24))) AS typical_hour_radians,
       ATAN2(AVG(SIN(2*PI()*EXTRACT(DOW FROM occurred_at AT TIME ZONE 'Asia/Seoul')/7)),
             AVG(COS(2*PI()*EXTRACT(DOW FROM occurred_at AT TIME ZONE 'Asia/Seoul')/7))) AS typical_dow_radians,
       COUNT(*) AS freq
FROM transactions
WHERE user_id = ?
  AND occurred_at < :targetDateTime
GROUP BY TRIM(LOWER(category))
```

Same `mode` vs `circular_mean` vs `none` open question for `typical_hour`/`typical_dow` applies here as in the sibling design — resolved by the same backtest grid search, run separately for this endpoint's own hit-rate metric (category top-1/top-5, not description).

**Imported-row midnight contamination applies here too, and likely worse.** The excel-import design stores date-only source rows at `occurred_at` = 00:00 (no real time-of-day signal), which the sibling `description` design already flagged as biasing `typical_hour` toward midnight for affected groups. `category` groups aggregate far more rows per group than `description` groups (categories are coarser than descriptions), so a `category` with a mix of imported (midnight) and live (real-time) entries will have its `typical_hour` pulled toward midnight by a larger fraction of its own history than a typical `description` group would. Circular mean limits but does not eliminate this. Not resolved here — same options as the sibling design: (a) accept the noise at this data scale, (b) add a `has_time` flag and exclude unknown-time rows from hour/dow scoring. Flag in the backtest report if held-out hit rate looks worse for categories with heavy imported-row share.

**Tie-breaking:** same 3-key deterministic sort as sibling design — `score` descending, `frequency` descending, `category` ascending (the returned original-spelling value, not the normalized key — same convention as `description`).

**Edge cases:**
- Fewer than 5 (or zero) qualifying categories: return however many qualify, never pad or error.
- No prior transaction exists (first-ever entry) in Stage 1: `priorCategory` term contributes 0 for every candidate — falls back to time/dow only.
- Empty history entirely: return empty list.

## Open Questions

- **Exact weight values** (`w_time`, `w_dow`, `w_prior`, `w_amount`) — not fixed; determined by backtest, run separately per stage.
- **Imported-row midnight contamination on `typical_hour`/`typical_dow`** — accept the noise, or add a `has_time` flag excluding unknown-time rows from hour/dow scoring (see Recommended Approach). Not resolved here; revisit if backtest hit-rate is visibly worse for import-heavy categories.
- **Backtest metric definition:** hit rate is measured as "was the actual `category` in the top-5 candidates," same shape as the sibling design — but Stage 1 and Stage 2 need separate backtest runs (different history-boundary/candidate-input each), doubling the backtest surface area versus the sibling design's single scorer.
- **Multi-user cold start** — out of scope, same as sibling design (single real user today).

## Success Criteria

Backtest harness (likely extends the sibling design's harness, same repo, same `history_strictly_before` convention), run against the same ~1 year of real history, **per stage**:

```
for each past transaction T (ordered by occurred_at):
  # Stage 1 pass
  candidates_s1 = recommendStage1(T.occurredAt, priorTransaction(before T), history_strictly_before(T.occurredAt))
  hit_s1 = T.category in candidates_s1.top5

  # Stage 2 pass
  candidates_s2 = recommendStage2(T.amount, T.occurredAt, history_strictly_before(T.occurredAt))
  hit_s2 = T.category in candidates_s2.top5
```

Train/test split (first ~80% train, held-out final ~20% eval) and naive-frequency baseline comparison — same rigor as the sibling design, applied independently to each stage. Target: no fixed number pre-committed; each stage's held-out hit rate versus its own naive baseline is the reference point.

## Next Steps

1. Extend or fork the sibling design's backtest harness to add Stage 1 and Stage 2 category scorers, using `TRIM(LOWER(category))` grouping from the start.
2. Grid-search weights per stage on the first ~80% of the year; evaluate once on the held-out 20%, compared against the naive most-frequent-category baseline, per stage.
3. Implement `RecommendationScorer` additions (or a new `CategoryRecommendationScorer`) with the two-stage formulas above — pure functions, unit-testable without Spring context.
4. Implement `GET /api/transactions/recommendations/category`, `user_id` from Spring Security principal, stage selected by `amount` presence, same `occurred_at < targetDateTime` boundary.
5. Tests mirror the sibling design's plan: scorer unit tests (per stage, tie-breaking, edge cases), repository integration tests (aggregation SQL, `TRIM(LOWER(category))` grouping, hour/dow representative-value methods, timezone boundary), controller tests (principal-scoped, stage switching on amount presence/absence).
6. Wire into real usage; watch whether category top-1 hit rate (the eventual "0-tap" bar) holds up on new entries — this is the number that would justify a future client auto-select feature, not built here.
