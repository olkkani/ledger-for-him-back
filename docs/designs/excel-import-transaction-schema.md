## Problem Statement

Frontend hands the backend `.xls`/`.xlsx` files exported from the user's existing 가계부 tracker. Header order as described by the user: 날짜, 자산, 분류, 소분류, 내용, KRW, 수입/지출, 메모, 금액, 환율, 자산 — 자산 appears twice in the source sheet (asset account, listed both early and late in the row); the original user description had "내용" appear twice, confirmed to be a typing typo, not two distinct content columns. All transactions are confirmed KRW-denominated with no foreign-currency activity, so the KRW/환율 columns are genuinely unused, not evidence of a currency-conversion requirement the design would otherwise miss. Exact distinct column count/order should still be confirmed against a real sample file before the parser is written (see parsing assumptions below) — the confirmations above resolve the *meaning* of the columns, not their exact position in the real file. The backend needs to extract 날짜, 분류, 내용, 수입/지출, 금액 and persist them; 소분류, KRW, 메모, 환율, and both 자산 columns are intentionally not imported in this pass. The open design question: model 수입/지출 as a separate type column with always-positive amounts, or fold direction into the amount's sign.

## What Makes This Cool

The prior design's recommendation engine and this one share the same table. Getting the schema right here means the backtest harness (from the prior design) and the "순자산 추이" home screen both read off one clean `SUM(amount)` — no CASE WHEN scattered across every query.

## Constraints

- Same stack as the prior design: Kotlin, Spring Boot, jOOQ + Flyway, Postgres. `V1.1__create-tables.sql` still empty — this is the first real migration.
- Only two transaction kinds exist: 수입, 지출. No transfers/investments planned.
- Source amount column in the spreadsheet is always positive; sign is not present in the raw file.
- Frontend's main screen is a 순자산 추이 (net worth over time) timeline/graph, i.e. income − expense as a running series — this is the dominant read pattern.

## Premises

1. Only income/expense exist as transaction kinds; no third type (transfer, investment) is planned. — agreed
2. The source amount column is always positive; sign is decided at parse time, not present in the file. — agreed
3. Because the main screen is a net-worth-over-time aggregate, query/aggregation simplicity outweighs 1:1 fidelity to the source spreadsheet's column layout. — agreed

## Approaches Considered

### Approach A: Signed amount, single column (chosen)
One `amount` column; 지출 rows are negated at parse time. No separate type column.

### Approach B: Type enum + always-positive amount
Separate `type` (INCOME/EXPENSE) column, `amount` always ≥ 0 — mirrors the source spreadsheet 1:1.

Rejected: every net-worth/timeline query (the app's primary screen) would need a `CASE WHEN type = 'EXPENSE' THEN -amount ELSE amount END` instead of a bare `SUM(amount)`. Also introduces an implicit invariant (type and amount's sign must always agree) that the DB doesn't enforce on its own. Better 1:1 traceability to the source file wasn't worth paying that cost on every read of the main screen.

## Recommended Approach

**Approach A: signed amount.** Parse-time rule: `amount = 수입/지출 == "지출" ? -금액 : 금액`. Store only the signed `amount`; do not persist a separate direction/type column.

### Import flow

```
POST /api/transactions/import  (multipart .xls/.xlsx)
  user_id ← authenticated session/principal (not read from the file)
  RowParser:    read workbook (Apache POI) → raw cell values, one sheet, header row 1
  RowValidator: 금액 > 0, 수입/지출 ∈ {"수입","지출"} after trim, 날짜 parseable
                → blank rows within the data range are skipped, not treated as invalid
  TransactionMapper:
    date        ← 날짜  (stored as TIMESTAMP at 00:00 — see schema below)
    category    ← 분류
    description ← 내용
    amount      ← 수입/지출 == "지출" ? -금액 : 금액   (금액 always positive in source)
  ImportService: validate ALL rows first; if every row is valid, insert all in one
                 DB transaction (all-or-nothing); if any row fails validation, insert
                 nothing and return the full list of row failures to the caller
```

Parser is split into three stages (RowParser / RowValidator / TransactionMapper) rather than one function, so each stage is independently unit-testable.

**Import transaction semantics — decided: all-or-nothing.** Validate every row before inserting anything; a single bad row rejects the whole file with no partial writes. A half-imported ledger is worse than a rejected upload — the user would have to manually diff which rows made it in. Rejected as too risky: partial-commit-with-report (valid rows insert, bad rows skipped) trades correctness for convenience on financial data.

**Parsing assumptions** (to confirm against a real sample file before writing the parser):
- Single sheet, header on row 1.
- 날짜 is an Excel date cell (not a string) — parse via POI's date handling, not string parsing.
- 금액 may contain thousands separators; strip non-numeric formatting before parsing to BigDecimal.
- Blank rows within the data range are skipped (not rejected) — Excel exports commonly have trailing/interstitial blank rows from formatting, and these are not genuine data errors.
- Non-multipart requests, wrong file extension (not .xls/.xlsx), and unauthenticated requests are rejected by the controller before parsing is attempted.
- Upload size/row-count limits, and rejecting encrypted/corrupt workbooks cleanly, are not yet specified — flagged by outside review (see Cross-Model Perspective), deferred to implementation time.

### Schema (extends the `transactions` table from the prior design)

```sql
-- transactions
user_id     -- from prior design
amount      -- signed: negative = expense, positive = income; NUMERIC precision/scale TBD at migration time
description -- from prior design (내용)
occurred_at -- TIMESTAMP, decided: unified across this design and the recommendation-engine
            -- design (which needs full timestamp for hour/dow scoring). This import's
            -- source (날짜) is date-only — stored at 00:00. See transaction-description-
            -- recommendation.md Open Questions for the follow-on effect on hour scoring.
category    -- new: 분류

-- duplicate protection: UNIQUE (user_id, occurred_at, description, amount)
-- relies on the DB constraint throwing on insert rather than a pre-insert query —
-- simpler and fast enough at personal scale; the all-or-nothing transaction means a
-- collision aborts the whole import and must surface a readable error, not a raw
-- constraint-violation message, to the caller.
```

`category` was part of the user's original 5-field extraction request (날짜, 분류, 내용, 수입/지출, 금액) from the start of this session — it's not a scope addition, just a column the prior design's minimal Next Steps #1 list (`user_id`, `amount`, `description`, `occurred_at`) hadn't listed yet because that design predates this import work. This import needs 분류 preserved even though the recommendation engine doesn't currently score on it.

**Migration sequencing note:** flagged by outside review — if `V1.1__create-tables.sql` has ever been applied to any environment (check Flyway's schema history table before editing), it cannot be edited in place; a new migration file is required instead.

**Edge cases:**
- 금액 parsed as 0 or negative, or 수입/지출 not exactly "수입"/"지출" after trim: rejected by RowValidator, which fails the whole import per the all-or-nothing decision above.
- Duplicate row (same user/date/description/amount already imported, e.g. a re-uploaded file): rejected by the unique constraint at insert time, which fails the whole import per the all-or-nothing decision above.

## Open Questions

- Whether `category`(분류) needs its own lookup table or stays a free-text column for now — deferred, not blocking the schema decision above.
- Upload size limits and hostile/corrupt/encrypted workbook handling — not designed this session, flagged by outside review as needed before this is a public-facing endpoint.
- Schema still needs nullability, `amount` precision/scale, an `amount <> 0` check constraint, and a `(user_id, occurred_at)` index (used by both this design's net-worth queries and the recommendation engine's history scan) specified at actual migration-writing time.
- **Outside-review flag, not yet resolved:** the unique constraint `(user_id, occurred_at, description, amount)` rejects legitimate same-day repeat purchases (e.g. two identical-price coffees same day) as false-positive duplicates, and cannot distinguish "retry of the same import" from "coincidental identical transaction." A more precise fix (import-batch identity for idempotency, row constraint only if true duplicates must be forbidden) was proposed but not adopted this session — revisit if real usage hits this false-positive case.
- **Outside-review flag, not yet resolved:** the recommendation API's `GET /api/transactions/recommendations?amount=...` doesn't yet state whether `amount` is signed post this design's decision, and grouping only by `description` can average an income and expense row sharing a label toward zero. Belongs to `transaction-description-recommendation.md`, not resolved here.
- **"순자산 추이" naming:** outside review noted `SUM(amount)` produces net cash flow, not true net worth (no asset-balance/opening-snapshot tracking). Naming/scope question for the product, not a schema blocker — noted, not resolved this session.

## Success Criteria

Import a real historical export file; `SUM(amount)` over the imported rows matches the total/balance figure the source 가계부 app or spreadsheet itself displays for that same period (not a separately-derived number) — that display is the ground truth to diff against. Per-row sign also matches the original 수입/지출 label for a manual spot-check sample.

## Cross-Model Perspective (Codex outside review)

Independent read after the 4-section review, given the locked decisions (all-or-nothing, DB-constraint duplicate check, TIMESTAMP unification, split parser, skip-blank-rows):

- The unique-key duplicate check is too strict — rejects legitimate same-day repeat purchases; a batch/file-identity approach for idempotency would be more precise. Not adopted this session (see Open Questions).
- Midnight timestamps on imported rows will poison the recommendation engine's `typical_hour` scoring — flagged as a follow-on in `transaction-description-recommendation.md` Open Questions; circular mean (already adopted there) limits but doesn't eliminate the effect.
- "All-or-nothing" needed to become a concrete implementation contract (validate-before-transaction, rollback on constraint violation with a readable error) rather than just a policy name — folded into the Import flow and Next Steps above.
- The parser plan was speculative (header position, format assumptions) before sampling a real file — folded into Next Steps as a required step before parser code is written.
- POI was named but never added as a dependency — folded into Next Steps #1.
- Migration-sequencing risk (editing an already-applied `V1.1`) — folded into the schema section and Next Steps #2.
- Schema under-specification (nullability, precision/scale, `(user_id, occurred_at)` index, `amount <> 0` check) — folded into Open Questions.
- Upload limits and hostile-workbook handling — folded into Open Questions and Next Steps #7.
- "순자산 추이" framing produces net cash flow, not true net worth — a product-naming question, noted but not resolved (out of scope for a schema design).
- Strategic alternative suggested: import into an append-only, provenance-preserving import-batch table first, then derive `transactions` — not adopted this session (would change the schema shape materially); left as a future option if retry-safety/diagnostics become a real pain point, not a blocker for the current design.
