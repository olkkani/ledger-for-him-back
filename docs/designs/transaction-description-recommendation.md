# Design: Amount-Based Transaction Description Recommendation API

Generated by /office-hours on 2026-08-23

## Problem Statement

Building a personal 가계부 (household ledger) backend in Kotlin/Spring Boot. When the user types an amount while logging a new transaction, the backend should recommend up to 5 likely descriptions based on the user's own transaction history — so entry can happen with fewer taps and less typing.

## What Makes This Cool

"학습이 눈에 보이는 것" — the recommendation visibly gets sharper the more the user logs. The user already has ~1 year of real usage data (hundreds to low-thousands of transactions), so this isn't a cold-start toy — it can be backtested against real history before it ever ships.

## Constraints

- Personal-scale data: hundreds to low-thousands of transactions per user. Real-time in-memory scoring is sufficient — no pre-aggregation table, no caching layer needed.
- Backend-only API (no client work in this design).
- Stack: Kotlin, Spring Boot, jOOQ + Flyway, Postgres (per `gradle/libs.versions.toml`). Schema is not yet created (`V1.1__create-tables.sql` is currently empty).
- Occasional backdated entries exist (logged the next day for yesterday), so "now" cannot be hardcoded into the scoring — it must be a parameter.

## Premises

1. Recommendation is a separate, synchronous GET endpoint, decoupled from the transaction-create endpoint. — agreed
2. The scoring reference time is a query parameter (`targetDateTime`), defaulting to `now()` if omitted — covers the common case (same-day entry) and the occasional backdated entry without extra complexity. — agreed (revised from "now always" after confirming backdated entries happen sometimes)
3. Recommendations are scoped to the logged-in user's own transaction history only — no cross-user data. — agreed
4. Candidates are grouped by unique `description`, not shown as raw individual transaction rows — avoids the same merchant appearing 2-3 times in a 5-slot recommendation list. — agreed
5. Similarity on amount uses **relative (percentage) difference**, not absolute won difference — a ±3,000원 window would swallow all small purchases into one bucket while being too tight for rent-sized amounts. — agreed
6. Weights for amount/time/dow are not guessed — they're chosen via backtesting against the user's existing 1-year history (see Success Criteria). — agreed

## Approaches Considered

### Approach A: Simple weighted sum score (chosen)
Score each historical `description` group by combining amount similarity (ratio-based), time-of-day similarity (hour distance), and day-of-week similarity (same weekday/weekend bucket) into one weighted sum, sorted descending, top 5. Simplest to implement and to tune via backtesting.

### Approach B: Staged filter then re-rank
Filter to descriptions within an amount tolerance band (e.g. ±20%) first, then re-rank by time/dow similarity within that band. Simpler to reason about per-stage, but needs a fallback when the filtered set has fewer than 5 candidates.

### Approach C: Vector/cosine similarity
Represent each candidate as a feature vector (log-amount, sin/cos-encoded hour, sin/cos-encoded day-of-week) and rank by cosine similarity. Most "principled," but overkill for a personal-scale dataset and harder to explain/debug.

## Recommended Approach

**Approach A: Simple weighted sum score.**

```
score = w_amount * amountSim(inputAmount, group.avgAmount)
      + w_time   * timeSim(targetDateTime.hour, group.typicalHour)
      + w_dow    * dowSim(targetDateTime.dayOfWeek, group.typicalDow)

amountSim = 1 - min(|abs(input) - abs(avg)| / max(abs(avg), 1), 1)   // compares magnitude only; sign (income/expense) is irrelevant to "does this look like a similar purchase"
hourDistance = min(|h1 - h2|, 24 - |h1 - h2|)          // circular distance, 0-12
timeSim   = 1 - min(hourDistance / 12, 1)
dowSim    = 1 if same weekday/weekend bucket else 0.3  // deliberately coarse: weekday-vs-weekend, not exact-day match
```

**Amounts are compared by absolute value.** This design doesn't assume or depend on how `amount`'s sign is stored (the separate Excel-import design settled on signed amounts, negative = expense) — `amountSim` always operates on `abs(amount)`, so recommendation quality is unaffected by that choice either way.

`group.typicalHour`/`group.typicalDow` — the representative-value method (mode, circular mean, or dropped entirely) is **not settled by architectural reasoning alone**; see Candidate aggregation and Success Criteria below. The backtest decides which method (if any) actually improves hit rate on real data — a circular mean is not obviously better than `MODE()` for a genuinely bimodal description (e.g. lunch-and-dinner spots), since averaging two clusters ~12 hours apart produces a near-zero, unstable resultant vector. Both are hypotheses to be tested, not settled choices.

Chosen because it's the fastest to build, the weights are directly interpretable, and — critically — it's the easiest to validate with the backtest harness below. Given real 1-year data already exists, the implementation cost of a "principled" vector approach isn't justified yet; this can be revisited later if backtested accuracy plateaus.

**Edge cases:**
- **Empty result / fewer than 5 candidates:** if the user has fewer than 5 unique descriptions total, or fewer than 5 score above zero, return however many qualify (including an empty list) — never pad or error.
- **`description` normalization:** grouping uses `TRIM(LOWER(description))` (see Candidate aggregation) so "Starbucks" and "starbucks " merge into one group; the response returns the most-recently-used original spelling for that group, not the normalized key.
- **Tie-breaking:** fully deterministic 3-key sort — `score` descending, then `frequency` descending, then `description` ascending (alphabetical). This guarantees the backtest is reproducible run-to-run even when score and frequency both tie.
- **High-variance amount groups:** a description repeated at very different amounts (e.g. a café bought both at ₩4,500 and ₩8,000) will have an `avgAmount` that doesn't closely match either real transaction. Left as-is for now — the backtest logs per-group amount variance so this can be diagnosed from real hit-rate data before investing in a fix (e.g. multi-modal amount clustering).

### API shape

```
GET /api/transactions/recommendations?amount={BigDecimal}&targetDateTime={ISO-8601, optional, default=now}

user_id is taken from the authenticated principal (Spring Security context), never
from a query parameter or request body — accepting it as client input would let one
user read another user's recommendation groups.

Response: List<RecommendationCandidate> (max 5)
  - description: String
  - score: Double
  - avgAmount: BigDecimal
  - frequency: Int
```

### Candidate aggregation

`MODE() WITHIN GROUP (ORDER BY x)` breaks ties by the ordering clause — for a column ordered by its own value, that means "smallest value wins," which silently biases every bimodal description (e.g. a lunch-and-dinner spot visited equally at 12:00 and 19:00) toward its earliest occurrence and never its latest. A circular mean avoids that specific bias but introduces its own failure mode: two clusters ~12 hours apart produce sin/cos vectors that nearly cancel, making the resulting "mean" unstable and not a meaningful center point. Neither method cleanly solves genuinely bimodal time patterns — **the backtest (Success Criteria) grid-searches all three options** (`mode`, `circular_mean`, `none` — i.e. drop the time signal for that group) and picks whichever wins on real hit-rate data.

`occurred_at` is `TIMESTAMPTZ`, and the app server's timezone is fixed to `Asia/Seoul` — single-user personal project, no per-user timezone needed. All `EXTRACT` calls run against `occurred_at AT TIME ZONE 'Asia/Seoul'` so hour/day-of-week boundaries don't shift with session or server timezone defaults.

```sql
-- Circular-mean variant (one of three backtested options — see above)
SELECT TRIM(LOWER(description)) AS normalized_description,
       (ARRAY_AGG(description ORDER BY occurred_at DESC))[1] AS description,  -- most recent original spelling
       AVG(ABS(amount)) AS avg_amount,
       ATAN2(
         AVG(SIN(2 * PI() * EXTRACT(HOUR FROM occurred_at AT TIME ZONE 'Asia/Seoul') / 24)),
         AVG(COS(2 * PI() * EXTRACT(HOUR FROM occurred_at AT TIME ZONE 'Asia/Seoul') / 24))
       ) AS typical_hour_radians,   -- convert back to 0-23 hour in application code
       ATAN2(
         AVG(SIN(2 * PI() * EXTRACT(DOW FROM occurred_at AT TIME ZONE 'Asia/Seoul') / 7)),
         AVG(COS(2 * PI() * EXTRACT(DOW FROM occurred_at AT TIME ZONE 'Asia/Seoul') / 7))
       ) AS typical_dow_radians,    -- convert back to 0-6 day-of-week in application code
       COUNT(*) AS freq
FROM transactions
WHERE user_id = ?
  AND occurred_at < :targetDateTime   -- excludes not-yet-happened future rows for backdated entries
GROUP BY TRIM(LOWER(description))
```

`hour_bucket`/`day_of_week` are derived from a single `occurred_at` timestamp column (see Next Steps #1) via `EXTRACT`, not stored as separate raw columns.

**Grouping uses `TRIM(LOWER(description))`** as the `GROUP BY` key, not the raw `description` — this is what makes the "trim/case-fold" edge case above actually true; grouping by raw `description` (as an earlier draft of this doc had) would silently contradict that claim. `ARRAY_AGG(... ORDER BY occurred_at DESC)` recovers the most-recently-used original spelling to show in the response.

**The `occurred_at < :targetDateTime` filter matches the backtest's `history_strictly_before` boundary exactly.** Without it, a backdated entry (logged today for yesterday) would aggregate against transactions that haven't "happened yet" relative to the entry's own timestamp — the production query and the backtest must use identical boundary semantics, or the backtested hit-rate number doesn't predict production behavior.

The DB does the grouping and aggregation (`GROUP BY` above) — the app layer only scores and sorts the already-grouped rows. Fetch all of the user's history once per request (personal scale — hundreds to low-thousands of rows) via this single query; do not additionally re-group in application code.

## Open Questions

- Exact weight values (`w_amount`, `w_time`, `w_dow`) are not fixed yet — determined by the backtest below, not guessed upfront.
- What happens when the user has zero or very few historical transactions (cold start for a *new* user, even though the current single-user data is rich) — out of scope for this design since only one real user exists today, but worth flagging before this ever supports multiple users.
- **Imported rows have no real time-of-day signal.** The Excel-import design (`excel-import-transaction-schema.md`) stores date-only source rows at `occurred_at` = 00:00. Circular mean (T1) prevents these from *biasing* other descriptions' `typical_hour`, but a description whose only occurrences are imported rows will still report a low-confidence "midnight" typical hour rather than an honest "unknown." Flagged during the excel-import design's eng review; not resolved here — options are (a) accept the noise at this data scale, (b) add a `has_time` flag and exclude unknown-time rows from hour scoring. Revisit if backtest hit-rate looks worse than expected on imported-heavy users.

## Success Criteria

Backtest harness, run against the existing ~1 year of real transaction history:

```
for each past transaction T (ordered by occurred_at, ties broken by id):
  candidates = recommend(T.amount, T.occurredAt, history_strictly_before(T.occurredAt))
  hit = T.description in candidates.top5
accuracy = hits / total
```

`history_strictly_before` is a datetime cutoff (not a date cutoff) — a transaction only "sees" prior transactions with an earlier `occurred_at`, so same-day-but-earlier entries count as history and nothing from the future leaks in. **This must match the production query's `occurred_at < :targetDateTime` filter exactly** — see Candidate aggregation above.

The harness recomputes each candidate group's stats (avg amount, typical hour, typical dow) in-memory per historical point, not via repeated Postgres queries — re-querying the DB per iteration would be awkward to write as a standalone script even though the absolute cost (low-thousands of rows, run once per iteration) stays well within a few seconds total.

**Train/test split, not a single full-year fit.** Grid-searching weights over the entire year and reporting hit rate on that same year overfits — the reported number would reflect how well the weights memorized this specific year, not how well they'll generalize to new entries. Split chronologically: grid-search `w_amount`/`w_time`/`w_dow` (and the `mode`/`circular_mean`/`none` hour-representation choice) on the first ~80% of the year, then evaluate the single best combination once against the held-out final ~20% — never re-tune against the held-out set.

**Baseline comparison.** Alongside the weighted-sum model's hit rate on the held-out set, compute the hit rate of a trivial "top-5 most frequent descriptions overall" baseline on the same held-out set. If the weighted model doesn't beat this baseline by a meaningful margin, amount/time/dow signals aren't adding value and the approach needs rethinking before shipping — this is what actually proves the design's premise, not hit rate in isolation.

Target: no fixed number pre-committed — the backtest result on the held-out set (compared against the naive-frequency baseline) becomes the reference point, and future changes to the algorithm are judged against whether they beat it.

### Test Plan (from /plan-eng-review)

- **`RecommendationScorer` (unit, JUnit5/Kotest — pure functions, no Spring context):**
  - `amountSim`: avg > input, avg < input, avg == input (score = 1)
  - `hourDistance`/`timeSim`: wraps midnight (23:00 vs 01:00 → distance 2), opposite time of day (distance 12)
  - `dowSim`: same weekday/weekend bucket, different bucket
  - Combined weighted-sum score across several weight combinations
- **Sort order (unit):** full 3-key deterministic sort — score descending, then frequency descending, then description ascending — produces a stable order even when score and frequency both tie.
- **Grouping/normalization (unit):**
  - `TRIM(LOWER(description))` merges casing/whitespace variants into one group
  - The most-recently-used original spelling (not the normalized key) is what's returned in the response
  - Fewer than 5 (or zero) qualifying candidates returns a short/empty list, never pads or errors
- **`TransactionRepository` (integration, Testcontainers Postgres):**
  - Each backtested hour/dow representative-value method (`mode`, `circular_mean`, `none`) produces the expected value for a known bimodal fixture (e.g. rows at both 9am and 9pm) — including the circular-mean near-zero-vector edge case for exactly-opposite times
  - `occurred_at < :targetDateTime` filter excludes rows at or after the given time (future-leak prevention)
  - `EXTRACT` results reflect `Asia/Seoul`, not UTC or server-default timezone, near a midnight boundary
- **`RecommendationController` (MockMvc/`@WebMvcTest`):**
  - `user_id` is read from the authenticated principal, not influenced by any request parameter
  - `targetDateTime` omitted → defaults to `now()`
  - `targetDateTime` provided → uses the given value
- **Backtest harness (standalone script, its own test):**
  - `history_strictly_before` excludes same-instant and future rows — no leakage from a transaction into its own or a later scoring pass

## NOT in scope

- **Multi-user cold start** (a brand-new user with no history) — deferred. Only one real user exists today; this becomes relevant only if the app ever grows beyond a personal tool.
- **Duplicate/near-duplicate `description` fuzzy matching** (e.g. "스벅" vs "스타벅스") beyond exact trim/case-fold normalization — deferred. Real usage data will show whether this is a meaningful loss before investing in fuzzy matching.
- **Caching or pre-aggregation layer** — explicitly rejected in Constraints given personal-scale data volume; revisit only if the row count grows by 1-2 orders of magnitude.
- **Reject-whole-file vs. skip-bad-row behavior for malformed import data** — this belongs to the separate Excel-import design (`excel-import-transaction-schema.md`), not this recommendation-API design.
